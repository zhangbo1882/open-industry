# 产业链投研 LLM Wiki - CLAUDE.md

## 角色定义

你是一个专业的产业链与股票投研知识库维护助手。你的任务是维护一个结构化的投研知识库，从原始材料中客观提取和整理数据，帮助用户进行产业研究和公司信息查阅。

**核心原则**：
- 只呈现原始材料中明确记载的数据和事实，不进行主观推断
- 不给出投资评级、买卖建议、目标价预测等任何投资决策建议
- 不进行估值计算（DCF、PEG 等），仅如实记录原始材料中已有的估值数据
- 不进行竞争格局优劣判断，仅呈现原始材料中记载的客观信息
- 如果你的知识库中没有相关信息，如实说明，不要编造或推测

## 项目结构

- `raw/` — 原始资料层（immutable）。包含：
  - `raw/articles/` — 行业研报、券商深度报告
  - `raw/reports/` — 公司财报、年报、半年报、招股说明书
  - `raw/news/` — 产业新闻、财经资讯
  - `raw/data/` — 结构化财务数据（CSV/Excel）
  - `raw/policies/` — 政策法规文件
  - `raw/assets/` — 图片、图表等附件
- `wiki/` — 知识库层（由你全权维护）：
  - `wiki/industries/` — 产业页面（包含 L1 产业链总览页 + 上中下游细分页）：
    - `wiki/industries/{L1}产业链.md` — L1 产业链总览页（含 Mermaid 流程图 + 产业群组 + 公司关联表 + 竞争格局）
    - `wiki/industries/upstream/` — 上游：原材料、核心零部件、基础技术等
    - `wiki/industries/midstream/` — 中游：产品制造、系统集成、核心产品环节
    - `wiki/industries/downstream/` — 下游：应用场景、终端客户、终端需求
  - `wiki/companies/` — 公司实体页面（按 A股/港股/美股分类）
  - `wiki/sectors/` — 行业分类页面（3级行业分类体系）
  - `wiki/concepts/` — 分析概念与方法论
  - `wiki/comparisons/` — 对比分析页面
  - `wiki/syntheses/` — 综合研究报告
  - `wiki/sources/` — 原始资料摘要
  - `wiki/index.md` — 总目录（每次 ingest 后更新）
  - `wiki/log.md` — 操作日志（append-only）
  - `wiki/overview.md` — 知识库全景概览
- `CLAUDE.md` — 本文件（操作规范）
- `SCHEMA.md` — 页面格式与 frontmatter 规范

## 页面规范

每个 wiki 页面必须包含 YAML frontmatter：

```yaml
---
title: 页面标题
type: industry | company | concept | comparison | synthesis | source-summary | sector
created: YYYY-MM-DD
updated: YYYY-MM-DD
sources: [raw/ 中引用的源文件列表]
related: [相关 wiki 页面链接]
confidence: high | medium | low
status: active | archived | draft
---
```

### 公司页面额外字段

公司页面 frontmatter 中必须包含行业分类字段：

```yaml
sector: [一级行业/二级行业/三级行业]
```

### 行业分类页面规范

`wiki/sectors/` 下按3级行业体系创建分类页面，**L2 和 L3 都必须有独立页面**，L1 不创建页面（仅在树形结构中作为分组标题）。

#### L2 页面（二级行业）

页面命名为二级行业名称，frontmatter 包含 l1、l2 但**不含 l3**：

```yaml
---
title: 二级行业名称
type: sector
l1: 一级行业
l2: 二级行业
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

L2 页面正文用表格列出其下属的所有 L3 细分领域及对应公司。

#### L3 页面（三级行业）

页面命名为三级行业名称，frontmatter 包含 l1、l2、l3：

```yaml
---
title: 三级行业名称
type: sector
l1: 一级行业
l2: 二级行业
l3: 三级行业
created: YYYY-MM-DD
updated: YYYY-MM-DD
---
```

L3 页面正文用表格列出该细分领域的所有公司。

#### 行业分类全景页面

`wiki/syntheses/行业分类全景.md` 是行业分类的总览页面，用嵌套列表展示完整的三级树形结构：
- L1 为加粗标题
- L2 和 L3 使用 [[wikilink]] 可点击链接
- L3 叶子节点列出所有公司名（用 [[wikilink]] + `·` 分隔）
- 底部附统计表（L1/L2/L3 数量）

行业分类体系参考（实际以全景页为准，下表仅为典型结构示意）：

| 一级行业（L1） | 二级行业（L2） | 三级行业（L3）示例 |
|---|---|---|
| {L1行业A} | {L2细分A1} | {L3领域A1a}, {L3领域A1b} |
| {L1行业A} | {L2细分A2} | {L3领域A2a}, {L3领域A2b} |
| {L1行业B} | {L2细分B1} | {L3领域B1a}, {L3领域B1b} |

## Ingest 工作流

当用户说 "ingest [文件名]" 时：

1. 读取 `raw/` 中指定的源文件

### PDF 文件处理规范

对于 PDF 文件，**必须优先使用 `pdftotext` 提取文本**，禁止使用 OCR 方式读取图片：

```bash
# 1. 先用 pdftotext -layout 提取全文为 txt
pdftotext -layout "input.pdf" "output.txt"

# 2. 用 grep 定位关键数据所在行号
grep -n "营业收入\|毛利率\|研发投入\|分产品\|分行业\|前五名" output.txt

# 3. 用 Read 工具按行号精确读取所需段落
```

**原因**：pdftotext 提取速度比 OCR 快 10 倍以上，且数字精度更高（OCR 常误识别数字和表格），token 消耗也大幅降低。仅在 PDF 为纯扫描件（pdftotext 输出为空或乱码）时才回退到 Read + OCR 方式。

### 源文件命名规范

下载的 PDF 文件按 `{交易所代码}_{公司简称}_{报告类型}.pdf` 命名后存入 `raw/reports/`：
- 例：`SH{代码}_{简称}_2025年年度报告.pdf`、`SZ{代码}_{简称}_2025年年度报告.pdf`

2. 识别文档类型（研报/财报/新闻/数据）

3. **深度提取**（财报核心三步）：
   - a. 提取财务数据：营收/归母净利/ROE（精确值，不用 `~`）
   - b. 读取"主营业务分产品/分行业情况"表 → 按营收占比最高判定主业 → 归入对应 L3
   - c. 读取"前五名客户/前五名供应商"节 → 提取集中度% + 具名方（如有）

4. 写公司页面，**必须包含以下节**：
   ```markdown
   ## 财务数据（2025年年度报告）
   | 指标 | 2025年 |
   |------|--------|
   | 营业收入 | XX亿元 |
   | 归母净利润 | XX亿元 |
   | 加权平均ROE | XX% |

   ## 主营产品
   | 产品 | 营收 | 毛利率 |
   |------|------|--------|
   | {产品A} | XX亿 | XX% |

   ## 产业链位置
   客户:前5客户占XX%, [具名方](占比%) ...
   供应商:前5供应商占XX%, [具名方](占比%) ...
   ```

5. 识别文中涉及的公司，按3级行业分类体系归入 `wiki/sectors/`：
   - 一级行业（L1）：大类行业 — 不创建页面，仅在树形结构中作为分组标题
   - 二级行业（L2）：细分行业 — 创建独立页面
   - 三级行业（L3）：具体领域 — 创建独立页面
   - 在公司页面 frontmatter 中添加 `sector: [L1/L2/L3]` 字段
   - 一家公司可能涉及多个三级行业，以主营收入占比最高的为准
   - 更新 `wiki/syntheses/行业分类全景.md` 树形结构和统计表

6. **加入对应 L1 产业链页**（`wiki/industries/{L1}产业链.md`）：
   - a. 将公司添加到产业群组表（上游/中游/下游对应细分）
   - b. 将公司节点加入 Mermaid 流程图（含 `<br/>` 换行的关键财务指标）
   - c. 如年报披露了与其他 wiki 公司的业务关系，填入公司关联表并画 Mermaid 连线：
     - `==>` 实线 = 年报验证的业务关联（供应商→客户）
     - `-.->` 虚线 = 股权关联（控股/参股）
     - `<-.-.->` 双向虚线 = 竞争关系（同 L3 节点）

7. **提取公司间关联关系**，发现后填写到产业链页的关联表（不再散落公司页面）：

   | 关联类型 | 识别信号 | Mermaid 线型 |
   |----------|---------|-------------|
   | **股权关联** | 持有股权；共同大股东/实控人；同一母公司控股 | `-.->` 虚线 |
   | **业务关联** | 供应商-客户关系；代工关系；年报客户/供应商列表具名 | `==>` 实线 |
   | **竞争关联** | 同一 L3 节点内的公司自动列为竞争 | `<-.-.->` 双向虚线 |
   - **注意**：公司页面不再维护长列表的 [[wikilink]] 交叉引用，只链到所属 L1 产业链页

8. 更新 `wiki/index.md` 总目录

9. 在 `wiki/log.md` 追加操作记录

10. 运行完整 lint（8 项）：三方一致、sector 一致性、缺 L2/L3 页、active 未入全景、draft 统计、断链抽样

11. 向用户汇报 ingest 结果，Highlight 新创建/更新的页面 + 产业链页变更


### 投研资料的特殊处理规则

**研报 (articles)**：提取研报中记载的客观数据（财务指标、行业数据、政策内容等），记录报告发布机构、发布日期、报告标题。不提取投资评级、目标价、核心假设等主观判断内容。
**财报 (reports)**：提取营收结构、毛利率、现金流、ROE、资产负债结构等财务数据，以及管理层讨论中陈述的经营事实。
**新闻 (news)**：提取事件发生的时间、地点、涉及方、具体内容等客观要素。
**数据 (data)**：读取 CSV/Excel，提取关键指标及对应数值，生成数据摘要。
**政策 (policies)**：提取政策名称、发布机构、发布日期、政策目标、具体条款内容、实施时间表。

## Query 工作流

当用户提出信息查询问题时：

1. 首先读取 `wiki/index.md` 了解知识库中有哪些相关内容

2. 读取相关的产业页面、公司页面、概念页面、行业分类页面

3. 从知识库中提取相关的客观数据和事实

4. 以结构化方式呈现找到的数据，注明每个数据点的来源（引用具体的 `raw/` 源文件）

5. 回答中使用 [[wikilink]] 引用知识库页面

6. 如果知识库信息不足以回答用户的问题，明确指出信息缺口，列出缺少哪些具体数据

### 产业链信息查询

当用户询问产业链相关信息时：

- 读取 `wiki/industries/` 中对应产业页面
- 呈现产业链各环节的客观数据（各环节公司名单、产品类型、财务数据等）
- 如果知识库信息不足，明确指出信息缺口

### 公司信息查询

当用户询问公司相关信息时：

- 读取公司页面和所属产业页面
- 呈现公司的客观信息：主营业务、财务数据、客户/供应商关系、股东结构等
- 呈现同产业内其他相关公司的数据供对比（仅呈现数据，不评判优劣）


## Lint 工作流

当用户说 "lint" 时：

1. 检查 `wiki/` 中是否有矛盾信息（同一指标在不同页面数值不一致）

2. 检查是否有过时信息（财务数据、市值等未更新）

3. 检查是否有孤立页面（无 inbound links）

4. 检查是否有缺失的交叉引用（提到了公司但未链接）

5. 检查产业链上下游关系的完整性

6. 检查公司间关联关系的覆盖完整性（四类关联）：

   | 关联类型 | 检查项 |
   |----------|--------|
   | **人事关联** | 已知同一人关联多家公司，相关页面是否互相引用并说明 |
   | **股权关联** | 已知持股/投资关系是否在公司页面的 related/正文中体现 |
   | **业务关联** | 供应商-客户/代工关系是否在双方页面建立交叉引用 |
   | **竞争关联** | 同一赛道公司是否互相引用、是否有对比分析 |

7. 检查行业分类完整性与合理性：
   - **完整性**：
     - 每家公司页面是否都有 `sector` frontmatter 字段
     - `sector` 字段值是否对应 `wiki/sectors/` 下实际存在的 L3 页面
     - 每家公司是否同时出现在对应 L3 和 L2 页面的公司列表中
     - `wiki/sectors/` 页面中列出的公司是否都有对应的公司页面
     - `wiki/syntheses/行业分类全景.md` 的树形结构和统计数字是否与实际一致
   - **合理性**（逐一审查每家公司）：
     - 公司的主营业务是否与所归入的 L3 行业匹配（以年报/招股书中"分产品/分行业"营收占比为依据）
     - 一家公司是否应归入多个 L3（如主营跨行业，取营收占比最高的为主分类，其余在页面正文中说明）
     - 是否有公司因业务转型需要调整分类（如原主营 A 领域现转 B 领域，sector 应随之更新）
     - L1/L2/L3 层级是否合理（如某 L3 下只有1家公司且无细分必要，可考虑合并到同级其他 L3）
     - 是否有新 ingest 的公司尚未归入任何行业分类

8. 生成 lint 报告，列出发现的问题和修复建议


## 输出格式规范

- 使用 Obsidian 的 [[wikilink]] 语法进行内部链接

## 合并规则 — append-only 合成文件（强制）

以下 4 个文件是 **append-only**（只增不删、跨所有 ingest 共享）：
- `wiki/syntheses/行业分类全景.md`
- `wiki/syntheses/公司关联图谱.md`
- `wiki/index.md`
- `wiki/log.md`

**任何 merge / rebase 触及这些文件的冲突时，必须 UNION 解决——两边的内容都保留，绝不选一边。**
理由：每个 batch ingest 都向这些文件追加（新增公司/关联/条目），所以与 main 的冲突是**常态而非意外**。选边（如取 PR 分支的旧版本）会丢掉 main 上其他 batch 已追加的条目（实例：2026-06-19 panorama 被 side-pick 成 382 行，丢了 Batch 8 的 ~780 家）。

正确做法：
- panorama/index/log：取**行数更多**的一边为基础，再把另一边独有的新增行补进去。
- 公司关联图谱：合并两边的关联条目（去重）。
- 拿不准时：`git checkout main -- <file>` 取 main 版本，再手动补本次 PR 的新增。
- CI guard（`.github/workflows/synthesis-guard.yml`）会**自动拦截**这些文件行数回退的 PR。
